## 4. Tag-based scenario selection

- [x] 4.1 **Design changed from the original plan per a later user request** (a generic tag-driven pair of scripts instead of one named script per tag): `cucumber.mjs` reads `tags: process.env.CUCUMBER_TAGS || undefined` (empty and unset both mean "every scenario", confirmed by `--dry-run` returning all 6 scenarios either way). Two new `package.json` scripts: `test:tag:parallel` runs `test:parallel` (whatever `CUCUMBER_TAGS` the caller set, e.g. via `cross-env CUCUMBER_TAGS="@organizations" npm run test:tag:parallel`) then `report` then `report:open`; `test:all:parallel` forces `CUCUMBER_TAGS=` empty first, so it always runs every feature regardless of an inherited env var, then the same report/report:open pair. Both use `(A) & (B && C)` rather than `&&` throughout, since `report`/`report:open` must still run even when the test run fails - confirmed via a `cmd.exe` probe that `&` (unlike the `exit` builtin) sequences unconditionally past a failing child process, which is what an actual failed `npm run test:parallel` produces. Verified live: `test:tag:parallel` with `CUCUMBER_TAGS="@organizations"` ran all 3 browsers, generated the report, and `report:open` served it; `--dry-run` confirms `CUCUMBER_TAGS=` runs all 6 scenarios and `CUCUMBER_TAGS="@organizations"` runs exactly 1. `report:open` is a long-running local server by design (matches `allure open`'s existing behavior) - it doesn't and isn't meant to exit on its own.

- [x] 4.2 User reported "the cleanup-before-run hook isn't working" when run via `test:parallel`/`test:tag:parallel` (3 concurrent `cucumber-js` processes, one per browser). Reproduced in isolation first: created a fake leftover org via a throwaway script, ran `cross-env CUCUMBER_TAGS="@organizations" cucumber-js` (single process) - the leftover was gone afterward, so `BeforeAll` itself works correctly for one process. Root cause was elsewhere: `organizations.feature`'s DataTable hardcoded the organization name as the literal `test-org`, and (a) `resolveOwnerCredentials()`/`resolveOwnerToken()` already resolve per-browser correctly (`GITEA_OWNER_<BROWSER>`/`GITEA_TOKEN_<BROWSER>`, confirmed by reading `credentials.ts`), but (b) Gitea organization names are unique across the whole instance, not per-user - so 3 concurrent processes each creating an org literally named `test-org` collide regardless of which of the 3 different owner accounts creates it. Fix: `organizations.steps.ts`'s "I create a new organization using:" step now builds the actual name as `` `${row.name}-${process.env.BROWSER ?? "local"}-${uniqueSuffix()}` `` (`uniqueSuffix` from `@gitea-automation/core-data-handler/data-handler.util`, the same helper `hooks.ts`'s `seededName()` and the Vitest suite's organization names already use), keeping the DataTable's `test-org` as a semantic prefix rather than the literal name. Verified: `npm run typecheck -w @gitea-automation/gitea-selenium-cucumber` and `npx eslint .../organizations.steps.ts` clean; `cross-env CUCUMBER_TAGS="@organizations" npm run test:parallel` now passes on all 3 browsers (exit 0 each), and a post-run check of `getUserOrganizations()` for all three owner accounts (chrome/firefox/edge) returned empty - no leftovers, no collisions.
