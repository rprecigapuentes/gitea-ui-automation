## 5. Follow-up: two locator/readiness bugs surfaced after archiving

The user reworked the `organizations.steps.ts` step this change added in 3.1: instead of `this.pages.orgFacade.waitForElements()`, it now calls `this.pages.orgRepositories.areOwnerElementsVisible()` and `this.pages.orgNavigation.areOwnerElementsVisible()` directly — made possible by the `orgRepositories`/`orgNavigation` getters added to `PageFactory` in 2.1. That surfaced two pre-existing bugs in those two fragments (both renamed from `isVisibleForOwner`/`isVisibleForMember` to `areOwnerElementsVisible`/`areMemberElementsVisible` by the user, alongside this change, in `business-logic/selenium/ui/pages/organizations/fragments/org-navigation.fragment.ts` and `org-repositories.fragment.ts`):

- [x] 5.1 `OrgNavigationFragment`'s new `tabsContainer` locator (`By.css(".overflow-menu-items']")`) had a stray trailing `']`, making it invalid CSS. `BaseComponent.isVisible()` catches the resulting `InvalidElementStateError` and reports `false`, so `waitForElements()` — and therefore `areOwnerElementsVisible()` — always returned `false`. Confirmed live against local Gitea with a throwaway Selenium script (created and deleted, not committed): `document.querySelectorAll(".overflow-menu-items']")` throws `InvalidElementStateError: ... is not a valid selector`; the real container is `<overflow-menu role="navigation"><div class="overflow-menu-items">`. Fixed to `By.css(".overflow-menu-items")`.
- [x] 5.2 `OrgRepositoriesFragment.waitForElements()` required both `searchBar` and `organizationSidebar` before reporting ready, but `searchBar` (the repository search input) only renders once the organization owns at least one repository — the org in this scenario has 0 repos at this point, so it never appears, and `waitForElements()` returning `false` made `areOwnerElementsVisible()` short-circuit to `false` even though the three owner-only buttons (`newTeamButton`, `newRepositoryButton`, `newMigrationButton`) were genuinely visible. Confirmed the same way (throwaway script: `searchBar` 0 matches, the three owner buttons 1 match each on a freshly created 0-repo org). Fixed `waitForElements()` to check only `organizationSidebar`, which is present regardless of repository count.

Verified: `npm run typecheck` (root) and `npm run lint` (root) clean; `cross-env BROWSER=chrome CUCUMBER_TAGS="@e2e" cucumber-js --format summary` (from `services/gitea-selenium-cucumber`) passed 1 scenario / 5 steps, confirming the reworked step now passes both assertions. A full `organizations.test.ts` Vitest run then progressed past this point and failed later, at an unrelated `#remove-team-member` timeout in the team-member-removal part of the flow — out of scope for this fix, left for a later session.
